- **多主架构**：总线上没有绝对的主从，任何节点都可以主动发送
    
- **广播式通信**：一帧数据发出去，所有节点都能收到

## 🔌 物理层

### 信号线

CAN 使用一对差分线：

|线|名称|含义|
|---|---|---|
|CAN_H|高线|差分正端|
|CAN_L|低线|差分负端|

差分信号的好处是：外界干扰同时作用在两根线上，接收端做差后干扰被抵消，所以抗干扰能力很强。

### 电平逻辑

|状态|CAN_H|CAN_L|差分电压|逻辑|
|---|---|---|---|---|
|隐性（Recessive）|2.5V|2.5V|~0V|1|
|显性（Dominant）|3.5V|1.5V|~2V|0|

**显性会覆盖隐性**，这是仲裁机制的基础。

### 终端电阻

总线两端各需要接一个 **120Ω** 终端电阻，用来匹配阻抗、消除信号反射。总阻值约 60Ω。缺少终端电阻会导致通信不稳定甚至完全失败。

### 比特率与线长

|比特率|最大总线长度|
|---|---|
|1 Mbps|40 m|
|500 kbps|100 m|
|250 kbps|250 m|
|125 kbps|500 m|
|50 kbps|1000 m|

比特率越高，传输距离越短。这是由信号传播时间和仲裁机制决定的。

## 📦 帧结构

CAN 有两种帧格式：**标准帧**（11 位 ID）和**扩展帧**（29 位 ID）。

### 标准数据帧

text

┌─────┬───────────┬────┬────┬─────────────┬─────┬─────┬─────┐
│ SOF │  仲裁段    │控制│数据│   CRC 段     │ ACK │ EOF │ IFS │
│ 1位 │ 11位ID+RTR │6位 │0-8 │ 15位CRC+1位  │ 2位 │ 7位 │ 3位 │
└─────┴───────────┴────┴────┴─────────────┴─────┴─────┴─────┘

| 字段        | 含义                    |
| --------- | --------------------- |
| **SOF**   | 帧起始，1 位显性             |
| **仲裁段**   | 11 位 ID + RTR 位，决定优先级 |
| **控制段**   | IDE、保留位、DLC（数据长度，0-8） |
| **数据段**   | 0~8 字节有效数据            |
| **CRC 段** | 15 位校验 + 1 位分隔符       |
| **ACK 段** | 发送方发隐性，接收方拉显性表示确认     |
| **EOF**   | 帧结束，7 位隐性             |
| **IFS**   | 帧间隔，3 位隐性             |

### 扩展数据帧

和标准帧的区别在仲裁段：29 位 ID 分为 11 位基本 ID + 18 位扩展 ID，中间有 SRR 和 IDE 位区分。

### 远程帧

RTR 位为显性时表示远程帧，用于**请求**某个 ID 的数据，本身不带数据段。

### 错误帧

任何节点检测到错误时，会发送错误帧通知总线上所有节点，让发送方重发。

### 过载帧

接收方来不及处理时，发送过载帧要求延迟下一帧。

## ⚖️ 仲裁机制

CAN 最精妙的设计之一。当多个节点同时发送时：

1. 每个节点边发边听总线
    
2. 发隐性（1）但听到显性（0）的节点，知道自己优先级低，**立即退出**，转为接收
    
3. 发显性（0）的节点继续发送
    
4. 最终 ID 最小的节点赢得仲裁，数据不丢失
    

**关键点**：仲裁是非破坏性的，赢家继续发，输家自动重试，不需要重发已发部分。

## 🛡️ 错误处理

CAN 有五类错误：

|错误类型|检测方式|
|---|---|
|位错误|发送的位和回读的位不一致|
|填充错误|连续 6 个相同位（位填充规则被破坏）|
|CRC 错误|接收方计算的 CRC 和收到的 CRC 不符|
|格式错误|固定格式字段出现非法位|
|应答错误|发送方没收到 ACK|

每个节点维护两个计数器：

- **TEC**（发送错误计数）
    
- **REC**（接收错误计数）
    

根据计数值，节点在三种状态间切换：

text

Error Active  →  Error Passive  →  Bus Off
   (正常)         (被动，少干扰)    (离线，停止发送)

**Bus Off** 是最严重状态，节点完全退出总线，需要软件干预才能恢复。

## 🔗 CAN FD 与 CAN XL

### CAN FD（Flexible Data-rate）

传统 CAN 的瓶颈是 8 字节数据和 1 Mbps 上限。CAN FD 做了两个改进：

- **数据段可变速率**：仲裁段仍用低速保证兼容，数据段可加速到 5 Mbps 甚至更高
    
- **数据长度扩展**：最大 64 字节
    

帧格式和传统 CAN 兼容，但需要控制器和收发器都支持。

### CAN XL

更新的标准，面向更高带宽：

- 数据段最高 **2048 字节**
    
- 速率可达 **10 Mbps+**
    
- 主要面向车载以太网和 CAN 混合的场景

## 🐧 Linux SocketCAN

Linux 把 CAN 设备抽象成**网络接口**，用标准的 socket API 操作。这是 Linux 上使用 CAN 最主流的方式。

### 核心概念

- CAN 接口名如 `can0`、`can1`，和 `eth0` 一样是网络接口
    
- 用 `ip link` 配置，用 socket 收发
    
- 支持真实硬件，也支持虚拟接口
    

### 常用命令

bash

# 安装工具
sudo apt install can-utils
# 配置并启动 can0，比特率 500k
sudo ip link set can0 type can bitrate 500000
sudo ip link set can0 up
# 查看状态
ip -details link show can0
# 监听
candump can0
# 发送标准帧
cansend can0 123#DEADBEEF
# 发送扩展帧
cansend can0 12345678#11.22.33.44

### 回环模式

用于本机测试，发出去的帧自己也能收到：

bash

sudo ip link set can0 type can bitrate 500000 loopback on

## 🧪 虚拟 CAN（vcan）

没有硬件时，用 vcan 在软件层面模拟 CAN 总线。

### 创建和使用

bash

# 加载模块
sudo modprobe vcan
# 创建接口
sudo ip link add dev vcan0 type vcan
# 启动
sudo ip link set up vcan0
# 测试
candump vcan0          # 终端 A
cansend vcan0 123#AABB # 终端 B

### 特点

|对比项|真实 CAN|vcan|
|---|---|---|
|物理层|差分信号|纯软件|
|比特率|受硬件限制|通常忽略|
|终端电阻|必须 120Ω|不需要|
|用途|实际控制|开发、测试|

## 📖 DBC 文件

DBC 是描述 CAN 通信协议的文本文件，相当于**翻译字典**：把原始字节翻译成有意义的物理信号。

### 核心内容

**报文定义：**

text

BO_ 291 EngineStatus: 8 ECU1

ID 291（0x123），8 字节，发送节点 ECU1。

**信号定义：**

text

SG_ EngineSpeed : 0|16@1+ (0.25,0) [0|16383.75] "rpm" ECU2

|部分|含义|
|---|---|
|`0\|16`|起始位 0，长度 16 位|
|`@1`|字节序（1=Intel 小端，0=Motorola 大端）|
|`+`|无符号（- 为有符号）|
|`(0.25,0)`|物理值 = 原始值 × 0.25 + 0|
|`[0\|16383.75]`|物理值范围|
|`"rpm"`|单位|
|`ECU2`|接收节点|

### 工具

- **cantools**（Python）：加载 DBC，解析/打包 CAN 帧
    
- **CANdb++**：Vector 官方 DBC 编辑器
    
- **python-can**：配合 DBC 做收发
    

### 典型用法

python

import cantools
db = cantools.database.load_file('vehicle.dbc')
msg = db.get_message_by_name('EngineStatus')
decoded = msg.decode(b'\x2f\x01\x64\x00\x00\x00\x00\x00')
print(decoded)  # {'EngineSpeed': 2500.0}

## 🤖 ROS 2 集成

ROS 2 通过 SocketCAN 桥接节点，把 CAN 帧转成 ROS 话题。

### 常用方案

|方案|特点|
|---|---|
|**ros2_socketcan**|Autoware 出品，功能完整，支持生命周期|
|**socketcan_adapter**|核心库与 ROS 包装分离，可复用|
|**nobleo_socketcan_bridge**|极简，低 CPU，无生命周期|

### 典型流程

text

CAN 总线 → SocketCAN → can 帧话题 → cantools + DBC → 解析后的信号话题

节点通常订阅 `/can_tx` 发送，发布 `/can_rx` 接收，消息类型是 `can_msgs/msg/Frame`。

### 开发流程建议

1. 先用 `vcan0` 把 ROS 2 节点逻辑调通
    
2. 硬件到位后切到 `can0`
    
3. 行为不一致时，再排查硬件、比特率、终端电阻、线序
    

这样能把软件逻辑错误和硬件电气问题分开定位。

## 🔧 常见问题排查

|现象|可能原因|排查方向|
|---|---|---|
|完全收不到数据|接口没 up|`ip link show can0`|
|偶发错误帧|终端电阻缺失|测总线阻值应为 60Ω|
|通信不稳定|比特率不匹配|确认所有节点比特率一致|
|Bus Off|错误计数超限|检查线序、干扰、终端电阻|
|只能发不能收|ACK 没人应答|确认总线上至少有一个其他节点|
|ROS 节点无数据|接口名写错|确认参数是 `can0` 还是 `vcan0`|
