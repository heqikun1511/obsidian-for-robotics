# 为什么要处理序号回绕

## 一句话概括

**因为 `sequence` 是 `uint16`，会从 65535 回绕到 0；如果不特殊处理，回绕瞬间"新序号"会被误判为"旧序号"，导致有效命令被丢弃——用 `int16_t` 转换可以正确判断"谁更新"，即使跨过回绕点。**

## 一、`uint16` 的回绕问题

### `uint16` 的范围

0∼655350∼65535

**发到 65535 后，加 1 回绕到 0**：

text

... 65533, 65534, 65535, 0, 1, 2, ...
                     ↑
                  回绕点

**协议第 8 节明确**：

> 树莓派从 0 开始，每发送一帧命令加 1，按 `uint16` 自然回绕。


## 二、直接比较会出错

### 场景：序号从 65535 回绕到 0

假设：

- `previous = 65535`（上一帧）
    
- `candidate = 0`（新帧，回绕后）
    

**如果直接比较**：

cpp

bool IsNewSequence(uint16_t candidate, uint16_t previous) {
    return candidate > previous;   // ❌ 错误做法
}

cpp

candidate > previous
0 > 65535   →   false   ❌

**结果**：`0 > 65535` 为 `false`，被判为"旧序号"——**丢弃了这个有效的新命令！**

**后果**：

- 回绕瞬间的命令被丢
    
- 若频繁发命令，可能连续丢多帧
    
- **控制延迟、甚至失控**
    

## 三、正确做法：用 `int16_t` 转换

### 代码

cpp

return static_cast<int16_t>(candidate - previous) > 0;


### 原理：利用有符号整数的"就近判断"

**关键**：`candidate - previous` 是**无符号减法**，结果按 `uint16` 回绕；**转成 `int16_t` 后，解释为有符号数**——这样"差值"落在 `[-32768, 32767]` 范围内。

### 验证回绕场景

text

previous = 65535
candidate = 0
candidate - previous
    = 0 - 65535
    = (uint16)(0 - 65535)          // 无符号减法，回绕
    = 1                            // 因为 0 - 65535 ≡ 1 (mod 65536)
    
static_cast<int16_t>(1) = 1 > 0   → true ✅

**正确判定为"新序号"！**
