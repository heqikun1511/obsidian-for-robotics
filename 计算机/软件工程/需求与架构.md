## 第六讲：需求和架构（1）

这一讲的核心判断是：**当 AI 让代码生成越来越便宜时，真正昂贵、也更值得投入精力的，是需求澄清、领域建模、架构边界与历史可追溯性。** 写出功能不再是最难的部分；难的是让系统能解释“为什么这样做”、承受下一次需求变化。[jyywiki.cn](https://jyywiki.cn/GSE/2026/lect6.md?utm_source=chatgpt.com)

### 1. 需求不是“功能列表”

用户说“我要一个教务系统”，远不是完整需求。学生、教师、教务员、财务等角色的目标可能冲突；正常流程之外还有转专业、缓考、课程替代、人工豁免等例外。

课程中的虚构案例很典型：

- 毕业总学分与分类学分必须同时满足；
- 高数 A 或“高数 B + 桥接课”都可满足数学要求；
- 算法课有先修课要求，但缓考学生可暂时选课；
- 两门交换课程可合抵一门课，却不能重复计入专业选修；
- 重修保留历史成绩，但学分只计一次，绩点按规则取较高成绩。

真正困难不在单条规则，而在于多条规则同时作用于一个学生。系统还必须为合规的特殊审批保留入口，并记录：**谁批准、豁免什么、面向谁、适用哪个规则版本、依据是什么。**

否则所谓“特殊处理”最后会退化成直接改数据库；而一旦只留下一个结果值，日后谁也无法分辨它是正常业务结论、正式特批，还是一次误操作。

### 2. MVP 能发现需求，但不能证明架构正确

MVP（最小可行产品）很适合快速让用户看到“选课”“课表”“毕业审核”等功能，从而暴露未被说出的需求。

但 MVP 通常只覆盖正常路径。系统第一次跑通，不代表它能处理：

- 规则变更；
- 历史数据迁移；
- 已审批例外；
- 多角色冲突；
- 数据更正后的连锁影响。

例如，把“一门交换课替代一门本校课”改为“两门交换课合抵一门必修课”，受到影响的将是课程映射、学分统计、毕业审核、成绩单、审批记录和测试，而不只是一个前端下拉框。

因此，软件复杂性的核心是**依赖传播**：一个结论依赖哪些事实、规则、审批与版本；其中任一环变化后，哪些结论需要重算、复核或保留历史。

### 3. 架构的本质：让变化有地方可去

架构不是“微服务”“数据库”“消息队列”的同义词，而是对以下问题的回答：

- 数据怎样流动？
- 状态由谁拥有？
- 模块之间允许依赖什么？
- 哪些变化应该局部化？
- 哪些事实和决策必须留下依据？

哪怕一个小程序也有架构。比如把程序拆成“读取 → 解析 → 处理 → 输出”，并不自动产生好架构；若各部分仍共享全局变量、依赖彼此内部细节，改动仍会扩散。

好的边界要落实为：

- 清晰的数据所有权；
- 可替换的输入/输出实现；
- 不泄露内部表示的接口；
- 围绕“可能变化的业务决策”来划分模块。

### 4. 汉诺塔：同一个问题，三种架构思维

课堂借“非递归汉诺塔”说明：代码复杂度往往来自表示方式，而不只是 `if` 或循环写得是否巧妙。

|视角|把复杂性放在哪里|特点|
|---|---|---|
|数学规律|步号、二进制末尾零、盘子移动方向|代码短，但依赖特定数学结构，规则变动后可能失效|
|显式任务栈|未完成任务及其分解关系|把递归隐含的调用任务显式保存|
|显式调用栈/栈帧|函数参数、程序计数器 `pc`、调用与返回|模拟抽象机器，可解释一般递归执行|

这三种实现都能完成汉诺塔，但它们对问题的解释不同。架构能力很大一部分就是：**选择一个更合适的表示，使变化与推理更容易。**[jyywiki.cn](https://jyywiki.cn/GSE/2026/lect6.md?utm_source=chatgpt.com)

### 5. 二维码 Excel 公式：当需求复杂到应当“造一个小编译器”

若要求“在 Excel 单元格输入文字，自动生成二维码”，直接生成大量 Excel 公式很脆弱：

- 括号、引用、数组计算混在一起；
- 改单元格位置、输入方式、Excel 版本或算法都会牵一发动全身；
- 公式难测试、难定位错误，也难复用。

更好的思路是建立中间表示 IR（Intermediate Representation）：

```
算法描述
   ↓
计算图 / IR：输入、常量、异或、查表、条件选择等节点
   ↓
不同后端
   ├─ Python 后端：便于测试与验证
   └─ Excel 后端：生成公式与布局
```

IR 的价值：

- 算法不必知道输入在哪个 Excel 单元格；
- 布局不必理解二维码编码；
- Excel 版本兼容只影响后端；
- 可进行常量折叠、公共子表达式复用；
- Python 与 Excel 后端可对同一输入交叉验证。

尤其要区分：

- **生成时（generation time）**：生成器提前展开固定结构、计算常量；
- **运行时（runtime）**：用户在 Excel 中修改的输入、由输入决定的条件分支。

如果把运行时输入也提前算掉，生成的只是一个固定二维码，而不是“可随输入变化的二维码工具”。

### 6. CRUD 的局限：当前状态会丢失业务含义

传统 CRUD 系统重点保存“现在是什么状态”：

```
can_graduate = true
```

但这个字段背后可能依赖：

- 成绩记录；
- 课程替代审批；
- 培养方案版本；
- 人工豁免；
- 当时的审核规则。

只保存 `true`，就丢掉了“为什么为真”。成绩修正或规则变化后，系统不知道该重算什么、复核什么，也无法解释历史决定。

因此，复杂业务系统中要额外保存：

```
结论 + 输入事实及版本 + 使用的规则版本 + 审批依据 + 时间
```

这里的时间至少可能有两种：

- **业务生效时间**：豁免从何时开始有效；
- **系统记录时间**：系统何时得知、何时录入该豁免。

这两个时间不同，才能解释“当时系统为什么拒绝、后来为什么应当重算”。

### 7. 组织改名案例：身份、属性、关系都不能混为一谈

“计算机系”变成“计算机学院”时，不能只问“要不要改 `dept_id`”。

应区分：

- **组织身份**：是不是同一个组织实体；
- **组织属性**：名称、层级、职责；
- **时间关系**：某学生、课程、权限在某时刻属于哪个组织；
- **承继关系**：新组织是否继承旧组织的部分职责或关联。

可能的处理：

1. 若组织身份持续：保持稳定 ID，名称和层级按有效期版本化。
2. 若产生新组织：创建新 ID，记录有日期的承继关系，并保留历史归属。

查询也必须明确口径：你要看“当时属于哪个组织”，还是“按今天组织架构重新汇总”？

### 8. 事件溯源：保存“发生过什么”，而不仅是“现在是什么”

事件溯源（Event Sourcing）将状态变化保存为一串业务事件：

```
选课申请已接受
成绩已登记
课程替代已批准
毕业审核已完成
```

当前状态不是唯一事实，而是这些事件应用后的结果：

```
事件流 + 投影（Projection） → 当前课表 / 成绩单 / 毕业审核视图
```

关键概念：

- **事件（Event）**：已经发生并被系统接受的业务事实；
- **投影（Projection）**：从事件构建某一用途的数据视图；
- **重放（Replay）**：重新应用历史事件来重建状态；
- **快照（Snapshot）**：避免每次从最早事件开始重放；
- **补偿事件（Compensating Event）**：错误不能偷偷覆盖，而应追加“更正了什么、为什么更正”。

事件溯源的优点：

- 可审计、可解释；
- 可回看某时刻状态；
- 可用新规则对旧事实重算；
- 有利于故障调查和迁移。

代价也很真实：

- 事件格式需要版本管理；
- 规则版本也需要管理；
- 重放必须隔离副作用，不能重新发短信、重复扣费；
- 事件不自动记录“推理依赖”，仍需额外保存审核所用规则与输入依据。[jyywiki.cn](https://jyywiki.cn/GSE/2026/lect6.md?utm_source=chatgpt.com)

### 9. 必须区分：恢复历史 vs 按新规则重新计算

这是本讲非常重要的区分。

|问题|含义|
|---|---|
|当时发生了什么？|使用当时的事实、规则、审批和输入，恢复历史解释|
|今天按新规则会怎样？|用新规则构建新的投影或重新审核|

例如，一名学生已按旧规则获得学位。今天修改规则后重新计算，不能让“当年授予学位”自动消失。若确需撤销，必须走新的业务流程，并记录新的事件和依据。

### 10. CQRS：写模型与读模型分工

CQRS（Command Query Responsibility Segregation）即命令查询职责分离。

- **命令（Command）/写模型**：表达业务意图，例如“申请选课”；负责检查资格、容量、时间冲突等业务约束。
- **查询（Query）/读模型**：为不同角色提供高效视图，例如学生课表、教师名单、教务统计。

它解决的是：**做决定的模型，不必等于展示结果的模型。**

注意：

- CQRS 可以在同一进程、同一数据库内实现，不等于必须微服务化；
- CQRS 和事件溯源可组合，但彼此独立；
- 异步更新读模型会导致短暂最终一致性，例如选课成功但课表暂未刷新；
- “最后一个名额”的竞争仍需并发控制，不能因为采用事件存储就自动安全。

### 11. DDD：让领域语义决定边界

DDD（Domain-Driven Design，领域驱动设计）强调软件结构应围绕业务概念，而不是围绕数据库表设计。

核心概念：

- **统一语言（Ubiquitous Language）**：开发者与业务人员对同一术语有一致理解；
- **限界上下文（Bounded Context）**：同一个词只在自己的边界内保持一致含义。

例如“学生”在不同上下文中含义不同：

|上下文|关注点|
|---|---|
|选课|资格、容量、时间冲突|
|财务|应收、缴费、退款|
|毕业审核|学分认定、培养方案、豁免|
|人事/组织|学籍、归属、身份变更|

“课程通过”不等于“可计入某专业毕业学分”。若把两者都压缩进一个 `passed` 字段，未来必然难以表达例外和规则差异。

### 12. 落地原则

对于已有复杂系统，不要一开始就全面重写或强上微服务。更实际的路径是：

1. 选一条高价值业务链，例如毕业审核。
2. 梳理它的事实来源、规则版本、审批流程、例外处理。
3. 记录“结论依赖什么”，而非只记录结论。
4. 新旧逻辑并行计算，重点核对特殊案例。
5. 明确权威写入口，逐步切换。
6. 对简单数据维护保留 CRUD；仅对确需追溯、重算、审计的业务引入额外架构。

一句话总结：**每多引入一层架构，都应回答：它让哪一种变化更容易？又增加了什么维护责任？**
