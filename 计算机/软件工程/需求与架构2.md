## 第七讲：需求和架构（2）

本讲继续回答一个核心问题：**好的架构究竟替我们做了什么？**

答案不是“让代码更时髦”，而是：面对持续变化的需求，架构通过合适的抽象、边界和组合规则，帮助有限的人脑驾驭复杂性，并为尚未出现的需求保留可扩展的解空间。[jyywiki.cn](https://jyywiki.cn/GSE/2026/lect7.md?utm_source=chatgpt.com)

### 1. 本质复杂性与附带复杂性

软件的复杂性分两类：

|类型|含义|教务系统例子|
|---|---|---|
|本质复杂性|业务世界本来就复杂，无法靠换技术消除|课程容量、先修要求、时间冲突、转专业后的课程认定|
|附带复杂性|实现和组织方式额外制造的麻烦|同一学生信息存五份、规则复制到多个页面、日期格式不统一|

需求工程的职责是面对本质复杂性，把模糊意图逐渐变成可执行、可检查的规约。例如“容量 100 人”还必须说明候补是否计入、预留名额能否借用、特批能否突破上限。

架构的职责则是：

- 分解本质复杂性；
- 减少附带复杂性；
- 明确数据归属、职责边界和模块接口；
- 让一次需求变更只影响少数应当变化的位置。

判断架构好坏最实用的问题是：

> 当需求改动一处时，系统里究竟需要改多少处？

### 2. 尊重“小脑袋”：枚举、归纳、抽象

Dijkstra 指出，人类能同时精确理解的内容非常有限。系统变大后，不能只靠“更努力地记住更多细节”。

三种重要的思维工具：

- **枚举**：检查有限的分支与情况；
- **归纳**：理解循环、递归和不变式；
- **抽象**：使用一个操作时，只依赖其承诺的效果，而不用每次展开内部细节。

“珍珠项链”比喻很好地说明了分层设计：

```
业务概念
  ↓
高层抽象
  ↓
中层机制
  ↓
底层数据结构与机器操作
```

每一层都做出一项设计决定，并向上提供更适合思考的概念。关键不只是“分了几层”，而是**细节是否被限制在应在的层内**。

例如，若过早把图像固定理解为“一行一行的像素”，后续所有模块都会被迫理解“行”的概念；若延迟这一表示决策，上层仍可只处理“图像”。

### 3. 对象与协程：两种不同的解耦

SIMULA 中的对象抽象解决：

> 哪些数据和操作属于同一个业务概念？

例如“课程”“学生”“订单”“机器”等对象，各自拥有自己的状态和行为。

协程（coroutine）则解决：

> 两个程序片段之间是否必须是调用者与被调用者的上下级关系？

子程序的控制关系是：

```
调用者 → 调用子程序 → 子程序返回 → 调用者继续
```

协程更像对等协作：

```
协程 A 运行 → 暂停并交给 B
协程 B 运行 → 暂停并交回 A
```

适合双方轮流推进、各自保留局部状态的场景，例如两个游戏程序对弈、生产者—消费者、仿真过程等。

### 4. 好架构设计的不是一个答案，而是一片解空间

本讲最重要的观点：

> 好的架构不是只解决今天的问题，而是为一类未来变化预留合理的落脚点。

这意味着要区分：

- 哪些选择现在必须固定；
- 哪些选择应该延后；
- 哪些接口可以稳定；
- 哪些实现应该允许替换；
- 使用者未来能在哪些位置创造新组合。

一个优秀的框架、协议或语言，价值往往不在于作者预先实现了多少功能，而在于后来人可以在其中做出多少作者没有预料到的东西。

### 5. UNIX：共同接口让工具能够组合

UNIX 哲学常被概括为：

1. 每个程序做好一件事；
2. 程序之间能够协作；
3. 用文本流作为通用接口。

重点其实在第 3 条。若没有共同接口，“单一职责”的工具仍只是一堆不能拼接的孤岛。

典型流水线：

```
cat books.json | jq -r '.books[].title' | fzf
```

这里：

- `cat` 提供原始数据；
- `jq` 提取书名；
- `fzf` 将候选交给人选择；
- 输出可继续交给下一个程序。

可靠组合依赖共同约定：

- 标准输入 `stdin`：输入数据；
- 标准输出 `stdout`：机器可处理的结果；
- 标准错误 `stderr`：诊断、日志、报错；
- 退出状态：成功或失败；
- `--`：结束选项解析；
- 输出格式稳定，机器输出中不要混入颜色、进度条和“操作成功”等文本。

工程上的启示是：

> 接口不只是“函数参数”。数据格式、错误通道、退出语义、边界条件，也都是接口的一部分。

### 6. 关系数据库：逻辑数据与物理存储分离

Codd 的关系模型实现了重要分离：

```
数据在逻辑上表示什么
        ≠
数据在磁盘、索引和执行计划中如何存储
```

以图书馆为例：

- 逻辑上有读者、书、馆藏和借阅关系；
- 可以查询“某人借了什么”“某书被谁借走”；
- 底层采用 B+ 树、哈希索引、全表扫描或何种存储页，不应改变业务查询的含义。

SQL 描述的是“我要什么结果”，优化器决定“怎样执行”。这使得：

- 应用开发者关注业务关系和约束；
- 数据库可独立演进索引、存储和查询计划；
- 双方拥有一定程度的独立演化能力。

### 7. Internet：变化中保持协作

Internet 通过分层协议提供稳定通信抽象：

```
应用：HTTPS
传输：TCP
网络：IP
链路：Wi-Fi / Ethernet / 光纤 / 蜂窝网络
```

应用不需要知道中间经历了什么路由、设备和物理链路。底层网络可持续更新，上层应用仍能演化。

Internet 架构的关键不是一张永远不变的“网络施工图”，而是一组允许局部替换、整体继续运行的协作规则。

### 8. 从“页面里写 SQL”到 MVC

最原始的 Web 应用往往是：

```
一个页面
  → 解析请求
  → 查询数据库
  → 写数据库
  → 拼 HTML 返回
```

这样很快能跑起来，但业务规则会复制、分散：

- 学生选课页检查一次容量；
- 管理员补选页再检查一次；
- 批量导入又复制一次；
- 规则更新时遗漏一个入口，系统就自相矛盾。

MVC 的分工：

|部分|职责|
|---|---|
|Model|业务数据、状态和业务规则|
|View|展示给用户的界面|
|Controller|接收输入，协调业务操作与响应|

在教务系统中：

```
“选课”请求
  → Controller 接收
  → Model 检查资格、容量、时间冲突
  → View 呈现成功或失败原因
```

重点不是目录里是否真的有 `Model/`、`View/`、`Controller/` 三个文件夹，而是：**同一项业务规则不能散落在多个页面和入口中。**

### 9. UI 也有自己的状态：MVVM、Vue 与 React

界面不只由数据库里的业务数据决定，还受大量 UI 状态影响：

- 搜索关键词；
- 当前选中行；
- 展开或折叠状态；
- 当前页面；
- 鼠标悬停；
- 表单输入但尚未提交的值。

可写成：

\[ \text{View} = render(\text{Model}, \text{ViewState}) \]

例如课程列表筛选：

```
courses + query → visibleCourses → View
```

`visibleCourses` 是由已有状态计算出来的派生值，不应再作为一份独立、手动同步的状态保存。

Vue 的典型表达：

- `ref` 保存响应式状态；
- `computed` 表达派生状态；
- `v-model` 将输入框显示值与输入事件处理连接起来。

React 的典型表达：

- `useState` 保存源状态；
- 渲染时从状态计算派生结果；
- `setState` 请求下一次渲染；
- 每一次渲染看到的是一份状态快照。

共同思想是：

> 让依赖关系显式出现，让框架沿依赖更新结果，而不是让程序员手工记住“改 A 后还要顺便改 B、C、D”。

### 10. MVC 不是复杂业务的终点

MVC 和 CRUD 适用于很多稳定的信息管理场景。但长生命周期业务，例如订单、财务、毕业审核，包含跨时间、多阶段、可撤销、需审计的过程：

```
下单 → 锁库存 → 支付 → 风控 → 发货 → 退款 → 售后 → 对账
```

仅仅把所有逻辑都塞进 `Model`，并没有减少本质复杂性。

会计是一个很好的例子。复式记账保证：

\[ 资产 = 负债 + 所有者权益 \]

每笔业务必须借贷平衡，但“账平”不代表“业务记对了”：

- 分类可能错；
- 原始凭证可能理解错；
- 同一笔交易可能重复录入；
- 金额正确但业务含义错误。

因此需要区分：

- 原始凭证；
- 业务解释；
- 受约束的记账动作；
- 账本规则；
- 派生报表。

### 11. LLM as a Compiler：让模型翻译，不让模型直接篡改结果

课程中的记账案例采用：

```
原始材料
  ↓
LLM 解释并生成受约束的业务动作
  ↓
确定性的规则程序执行动作
  ↓
账本状态、资产负债表、利润表、现金流量表
```

这里 LLM 类似“编译器前端”：

- 将自然语言凭证翻译成系统定义的操作；
- 不直接让模型逐格填写报表；
- 规则程序负责检查金额类型、账户约束、余额条件和状态变化；
- 人仍需审查模型生成的动作是否符合真实业务。

这是一种很值得复用的 AI 系统设计：

> 把 LLM 放在“理解与翻译”的位置；把关键约束、计算与状态变换放在可验证、可重放的确定性程序中。

### 12. 把过去、现在、未来分开

复杂业务经常把三件事混在一个“状态”里：

|时间维度|应表达什么|
|---|---|
|过去|已发生、可确认的事实|
|现在|基于历史事实和规则计算的状态或视图|
|未来|计划、命令、合同、预期、待执行任务|

例如：

- “已支付”是事实；
- “当前余额”是从事实计算出的状态；
- “计划下周付款”是预期，而不是事实。

事件溯源的价值，是把过去保存为事件流，把当前状态作为投影，把未来作为尚未兑现的意图。

退款与“从未支付”可能有相同净现金变化，但绝不是相同历史。系统要保留这种差异，才能审计、解释与修复。

### 13. 教务系统：让毕业结论可追溯

不要把下列内容都当作可随意修改的独立字段：

```
成绩记录
已修课程列表
总学分
分类学分
是否满足毕业条件
```

它们中许多其实是派生关系：

```
选课、成绩、认定记录
  ↓
已通过课程
  ↓
分类学分、去重、替代关系
  ↓
培养方案规则
  ↓
课程准出结论
  ↓
毕业设计、资产归还等其他条件
  ↓
最终毕业审核
```

成绩复核从“不通过”改为“通过”后，系统应：

1. 保存这次更正及其依据；
2. 找到依赖该成绩的派生结果；
3. 重新计算已通过课程、学分、审核结论；
4. 保留变化前后为什么不同的解释。

而不是让管理员手工去改“总学分”“已修课程”“毕业状态”等多个副本。

### 14. 从状态一致性转向计算正确性

传统系统最常问的是：

> 多份状态是否保持一致？

本讲进一步提出：

> 这些派生结果是否真的由正确输入、规则和计算得到？

SQL、缓存、前端状态、应用代码中都存在派生数据。架构要尽量显式表达：

```
这个结果依赖什么？
依赖变更后谁负责更新？
如何判断结果已经失效？
怎样解释它的来源？
```

MVVM、React、Dataflow、Event Sourcing 处于不同层次，但都有共同方向：**把数据依赖与派生关系显式化。**[jyywiki.cn](https://jyywiki.cn/GSE/2026/lect7.md?utm_source=chatgpt.com)
