这一讲从“如何让 Agent 写代码”进一步走向“如何组织一个能持续开发、验证、修正的软件生产过程”。

核心结论是：

> Agent Native 开发不是让 AI 替人写代码，而是把 Agent 视为真正参与项目的开发者，并为它设计可观察的工作区、明确的约束、自动化反馈和可追溯的状态迁移。

---

## 1. 原型必须尽早运行：Let it fail

软件工程中始终存在三层鸿沟：

```
Intent（人的意图）
    ↓
Spec（规格）
    ↓
Implementation（实现）
```

即使当前规格看似明确，也必须尽早做出可运行原型。因为原型会暴露三类错误：

1. 实现没有满足规格；
2. 规格没有表达真正需求；
3. 规格中关于用户、规模、并发和运行环境的假设不成立。

例如，选课系统在纸面上完全正确，但两个学生同时抢最后一个名额时，可能出现超卖、重复提交或状态不同步。

“Let it fail”不是允许敷衍，而是让失败成为观察现实和修正判断的机会：

```
原型
  → 观察行为与失败
  → 修实现 / 修规格 / 修架构
  → 形成下一轮原型
```

## 2. Ralph Loop：同一个提示词，变化的是工作区

Ralph Loop 的最简形式：

```
while true; do
    cat PROMPT.md | claude -p
done
```

其价值不在死循环，而在于：

```
提示词保持不变
工作区状态不断改变
```

每轮 Agent 都做类似事情：

```
读取当前任务与工作区
  → 检查已有成果
  → 选择下一项工作
  → 修改代码/文档/测试
  → 运行验证
  → 把结果留在工作区
```

下一轮 Agent 即使没有上一轮对话历史，也能从文件、日志、测试结果和待办事项继续推进。

因此，长期任务不应依赖越来越长的聊天记录，而应依赖一个可恢复的 Workspace。

## 3. Workspace 是状态，Agent 是状态迁移

可把 Agent 开发理解成状态机：

```
Workspace = State
Agent 工作 = Transition
```

工作区不只有代码，还应包括：

```
需求与验收标准
设计决策
当前实现
测试与测试数据
构建产物
运行日志
失败记录
TODO
已知风险
```

一个好的交接状态不是：

```
“选课功能完成了”
```

而是：

```
普通选课路径已通过；
最后一个名额的并发测试失败；
复现命令为 xxx；
失败日志在 logs/capacity-race.log；
怀疑库存检查与写入未处于同一事务。
```

这才使下一轮 Agent、人类开发者或 CI 能够恢复判断，而不是重新摸索。

Git/Jujutsu 则让状态可以分叉：

```
main
 ├─ Agent A：修复容量并发
 ├─ Agent B：补充端到端测试
 └─ Agent C：整理领域规则文档
```

但“能并行”不等于“并行一定有收益”。如果所有 Agent 都面对同一个模糊失败，它们可能重复工作、互相覆盖；任务划分与集成检查仍然必要。

## 4. 每次状态迁移都要检查：CI/CD 的本质

Ralph Loop 的关键并非“反复尝试”，而是：

> 每次修改后都验证，只有通过条件的状态才能继续被接受。

这其实就是 CI/CD 的第一原则：

```
开发者不可信
包括人类开发者和 Agent
```

因此要把“好状态”写成可执行标准：

```
能构建
测试通过
Lint 通过
旧功能没有被破坏
架构约束仍被遵守
部署产物可生成
```

对应关系：

|概念|含义|
|---|---|
|CI|高频集成小改动，并自动构建与验证|
|Continuous Delivery|软件始终保持可发布状态，由人决定何时上线|
|Continuous Deployment|通过验证后自动部署上线|

CI/CD 并不神秘，本质是：

```
某个事件发生
  → 执行确定动作
  → 根据结果允许或阻止后续状态
```

例如：

```
push / merge request 更新
  → Lint
  → 单元测试
  → 集成测试
  → 允许或禁止合并
```

## 5. CI/CD 本身也是业务规格

真正困难的不是写出 YAML，而是定义流程规则：

- PR 有新提交时是否重新检查？
- 是否检查“PR + 最新 main”的组合？
- 两个 PR 各自通过、合起来失败怎么办？
- 测试偶发失败可重试几次？
- 紧急修复谁能绕过检查？
- 绕过后如何记录和补测？
- 多次部署重叠时，如何防止旧构建覆盖新版本？

一个可靠发布流程可表达为：

```
PR 更新
  → Lint + Test
  → 与最新 main 合并后的验证
  → 失败：禁止合并

main 更新
  → Lint + Test + Build
  → 全部成功：部署这次构建产物
  → 任一步失败：保留上一线上版本
```

验收 CI/CD 时必须测试失败路径：

1. 故意制造 Lint 错误，确认确实无法合并；
2. 故意让测试失败，确认不会部署；
3. 修复后确认能恢复正常发布。

检查“显示了红叉”不够；要检查“门确实关得住”。

## 6. Agent 时代，CI 更重要

Agent 能迅速生成大量代码，也能迅速制造大量技术债。典型风险包括：

- 一句能说清的内容写成几十 KB 文档；
- 同一规则在多个文件重复；
- 过度设计、过度防御；
- 功能能跑，但人类难以理解和维护；
- 为通过狭窄测试而钻空子；
- 修改测试去迁就错误实现。

因此，工程品味不能只写成：

```
“请保持代码简洁”
```

而应尽量转化为可检查机制：

|风险|可执行约束|
|---|---|
|格式混乱|formatter / lint|
|禁止的模块依赖|import 方向检查|
|重复逻辑|重复代码检测 + 人工裁决|
|入口文档膨胀|入口文件尺寸与结构约束|
|复杂函数|圈复杂度、函数长度检查|
|缺失关键日志|日志字段契约检查|
|测试被篡改|测试目录权限、外部验收场景|

形成闭环：

```
CI 阻止
  → Agent 读取明确失败信息
  → Agent 修复代码
  → 同一规则重新验证
```

但有一条红线：

> 实现 Agent 不能因为测试失败，就自行删除断言、降低阈值或修改验收标准。

“删掉测试得到绿色”和“修好程序得到绿色”，表面相同，工程含义完全不同。

## 7. Harness：把工程知识变成 Agent 可用环境

Harness 可以理解为 Agent 的工程工作装备，包括：

```
任务指令
项目知识
工具权限
运行环境
测试与验证
架构约束
状态记录
版本管理
反馈循环
```

Agent Native 的重点不是“代码由 AI 写”，而是把人脑中的工程经验外部化，让 Agent 找得到、看得懂、能验证。

一个适合你的 ROS 2 工程可以这样组织：

```
AGENTS.md
├─ 项目总入口、常用命令、禁止事项
docs/
├─ architecture.md       # 节点边界、数据流
├─ decisions/            # ADR：关键设计决定与理由
├─ hardware/             # CAN、传感器、设备约束
├─ testing.md            # 仿真与验收方式
scripts/
├─ lint.sh
├─ test.sh
├─ run_sim.sh
└─ verify_topics.sh
tests/
├─ unit/
├─ integration/
└─ scenarios/
```

其中 `AGENTS.md` 应是索引，不是把所有知识塞进一个超长 Prompt。

高价值原则：

1. **让 Agent 找得到知识**：工程约定、设备事实、接口说明、设计理由均进入版本管理；
2. **让 Agent 看得见程序行为**：独立工作区可启动仿真、查看日志、复现问题；
3. **让品味变成规则**：如禁止节点直接跨层访问硬件、topic 命名必须可 namespace 化；
4. **让清理持续发生**：小步重构与清理，而不是积累到不可维护才重写。

## 8. 三个有代表性的工程实践

### Stripe Minions：固定流程交给程序

Stripe 的经验是区分两类工作：

```
需要理解和选择的工作
  → 交给 Agent
确定、重复、每次都必须执行的工作
  → 交给普通程序
```

例如：

|工作|执行者|
|---|---|
|实现功能|Agent|
|阅读 CI 报错并修复|Agent|
|执行 Lint|脚本|
|执行测试|脚本|
|推送分支|自动化流程|
|重试次数上限|工作流规则|

启示：不要每一步都问模型“要不要运行测试”；测试本就必须运行，就把它写死在流程中。

同时要有重试上限。连续失败且没有新信息时，应停下来升级问题，而不是无限消耗 Token。

### Anthropic C 编译器：验证方式决定任务能否并行

16 个 Agent 同时编译 Linux，最初却都被同一个错误卡住，重复修复、互相覆盖。

后来通过 GCC 作为可信参考：

```
大多数文件 → GCC 编译
少数文件 → 新编译器编译
失败时逐步切换文件集合
  → 缩小故障范围
```

这说明：

> 在增加 Agent 数量之前，先改善任务表示和反馈粒度。

如果反馈只有“整个系统失败”，所有人都会冲向同一个入口；如果能把失败缩小为独立子集，才可能真正并行。

### StrongDM：外部验收场景与数字孪生

内部单元测试可能被 Agent “刷分”：

```
return true
```

或通过修改测试来让错误实现通过。

因此可将端到端用户故事组织成独立的验收场景，甚至放在主代码库外部。例如选课系统：

```
场景 A：最后一个名额同时被两个学生申请
场景 B：请求已被服务端接受，但响应在网络中丢失
场景 C：课程替代审批在审核后才录入
```

对于依赖外部 API 的项目，可建立行为替身/数字孪生，在真实系统对照验证后，高频复现边界情况和故障。

## 9. 持续清理不等于解决架构问题

持续格式化、去重、补文档、修正接口，类似工程层面的“垃圾回收”。

它重要，但解决不了已经失效的核心假设。

Friendster 的案例说明：

```
单主写库
  + 多个完整读副本
```

在用户和写入量小的时候可行；写入增长后，每个副本都要复制所有更新，写入、I/O 与复制延迟成为瓶颈。继续整理局部代码，无法改变这一负载结构。

这类问题需要架构重构，例如按用户分片，而不只是“多加几个副本”。

关键区别：

```
局部缺陷
  → 修复、重构、持续清理

错误的系统前提
  → 改变架构、数据模型或业务假设
```

更难的是：看出要改还不够，组织必须有能力迁移数据、重排协作、安排上线并承受过渡成本。

## 10. 好想法也可能在需求验证上失败

AI 让开发便宜，不会自动让产品成功。

两个案例：

- **Webvan**：网上买菜并非没有需求，但重资产仓配能力远高于实际订单密度时，错误的需求判断会被基础设施成本放大。
- **Quibi**：内容、技术和产品形式都具备，不等于用户需要一个独立的精品短视频服务。

工程上的启示：

```
功能越来越多
≠ 用户价值越来越高

局部测试越来越绿
≠ 核心需求假设已经成立

代码越来越完整
≠ 架构方向正确
```

Agent 很容易让产品“slop 化”：页面、功能、文档快速堆积，但重复、冗余和未经验证的关键假设也一同堆积。

因此：

```
原型 → 获取现实反馈
反馈 → 修改判断
重构 → 改变结构
```

三者必须构成循环。

---

## 11. 本讲最重要的总结

```
Agent Native 开发
≠ 把需求交给 AI，等它写完

Agent Native 开发
= 为 Agent 构造一个可持续改进的软件生产环境
```

这个环境需要：

```
明确 Spec
+ 可恢复 Workspace
+ 小步状态迁移
+ 自动构建与测试
+ 有约束力的 CI 门控
+ 真实或模拟的验收场景
+ 可检查的架构规则
+ 版本控制与回滚
+ 持续小规模清理
+ 在失败后愿意改变架构判断
```

最终培养的不是“会不断调用 Agent 的人”，而是能让每次尝试都留下证据、反馈和更好下一步的人。课程强调，实践机会会积累成工程判断力；Token、工具和 Agent 提供更多尝试机会，但只有能读懂失败、提炼经验并改变下一轮设计的人，才能真正从中受益。
