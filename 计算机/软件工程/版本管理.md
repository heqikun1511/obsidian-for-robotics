## 1. 项目不只是“一堆文件”

一个软件项目包含多种制品（artifact）：

- Intent：想解决什么问题；
- Spec：应满足什么规格；
- Impl / Code：如何实现；
- 测试、配置、文档、构建产物等。

文件和目录树是非常成功的工程接口：人可以编辑，工具可以搜索、构建、比较，Git 可以版本化。但“文件放在同一个目录”不代表它们的关系被表达了。

例如你的 AMI 项目中：

```
需求：从 VCU CAN 读取转速并显示换挡提示
    ↓
CAN 报文定义 / 信号定义
    ↓
ESP32-P4 CAN 解析任务
    ↓
LVGL 仪表盘页面与 WS2815 灯带控制
    ↓
CAN 回放测试、实车台架测试
```

真正困难的不只是“哪个文件改了”，而是：

- 这个 CAN 信号变更会影响哪些页面、控制策略和测试？
- 某段代码对应哪条需求？
- 某个测试是在验证哪个设计假设？

这叫 **可追踪性（traceability）**：维护需求、设计、实现、测试之间的联系。Git 保存文件历史，但不会自动替你维护这些语义关系。[jyywiki.cn](https://jyywiki.cn/GSE/2026/lect4.md?utm_source=chatgpt.com)

## 2. Git 保存快照，但“提交”不等于“变更本身”

Git 中一次 commit 同时包含：

- 某一时刻的文件快照；
- 父提交；
- 作者与说明等元数据。

因此 commit 形成一张 DAG（有向无环图）。

问题在于：人理解的“一个功能改动”，和 Git 中的 commit ID，不总是一回事。

例如：

```
C：增加 CAN 信号校验
```

后来主线更新，你执行 rebase：

```
C → C'
```

`C'` 有新的父提交，因此 commit ID 一定变化；但从工程意图上，它仍然是“增加 CAN 信号校验”这同一个变更。

所以要区分：

|概念|关注点|
|---|---|
|Commit|某个具体快照版本及其历史位置|
|Change|一项持续演化、可能反复修改或重放的工程变更|

## 3. Jujutsu（jj）：把“变更的身份”作为一等概念

Jujutsu（常写作 `jj`）是一个值得学习的新版本管理系统。它保留 Git 的底层快照思想，但引入两种 ID：

|ID|含义|
|---|---|
|`commit ID`|某个具体版本的身份；rebase 后会变化|
|`change ID`|一项持续演化的改动身份；rebase 后通常保持不变|

也就是说：

```
原提交 C       → change-id: X
rebase 后 C'   → change-id: X
```

你能表达：“版本变了，但它仍是同一个功能变更。”

这更符合人对开发工作的直觉：我不是“创造了另一个功能”，而是把原功能放到新的基础上继续适配。

### jj 的两个重要设计

1. **工作区自然地处于一个可修订提交中**

Git 的典型操作是：

```
编辑 → git add → git commit
```

jj 更接近：

```
编辑 → 当前变更自动更新为新快照 → 随时继续修订
```

它弱化了日常对独立暂存区的依赖，体验更像不断 `commit + amend`。

2. **冲突可以作为持久状态保存**

Git rebase 发生冲突时，通常会中断流程，必须先解决冲突才能继续。

jj 可以把“含冲突的变更”保存下来：

```
先完成历史重写
→ 冲突作为变更的状态保留
→ 稍后再解决冲突
```

这很重要：冲突不再只是阻塞操作的异常，而成为系统能够表达、保存、继续处理的状态。[jyywiki.cn](https://jyywiki.cn/GSE/2026/lect4.md?utm_source=chatgpt.com)

## 4. Agent 并行开发：不能共用同一个工作目录

如果多个 Agent 同时改同一份目录，会出现典型竞态：

- Agent A 读到旧代码；
- Agent B 改了文件；
- A 仍基于旧理解修改；
- 测试运行时，其他 Agent 又修改了实现。

“给 Agent 起不同名字”不意味着它们拥有隔离的开发环境。

### Git worktree

可以用 `git worktree` 给每个 Agent 单独工作目录、分支与暂存区，同时共享同一仓库对象：

```
git worktree add -b agent-ui ../project-ui
git worktree add -b agent-memory ../project-memory
```

适合这样的拆分：

```
agent-ui       → 仪表盘 UI / LVGL 页面
agent-can      → CAN 报文解析与状态机
agent-test     → 回放数据、单元测试、文档
```

优点：

- 工作文件不会互相覆盖；
- 各自可独立测试；
- 不必在本机 agent 间反复 push / pull。

但 worktree 并不能解决语义协作问题。例如 UI 等待的 RPM 字段单位是 `rpm`、`rps` 还是 `0.1 rpm`，仍必须通过接口文档、任务边界与测试约定解决。[jyywiki.cn](https://jyywiki.cn/GSE/2026/lect4.md?utm_source=chatgpt.com)

## 5. 两种并发策略：先做后合并 vs 先上锁

### 策略 A：乐观并发

```
各自基于快照开发
→ 最后 merge / rebase
→ 处理冲突并验证组合结果
```

这和 Git 的自然工作方式接近，也可类比数据库中的 MVCC：允许多个版本并存，之后再协调。

优点：并行度高。  
风险：最后可能出现高代价冲突，甚至“文本无冲突但逻辑冲突”。

### 策略 B：悲观并发 / 互斥锁

```
申请共享资源锁
→ 获取最新状态
→ 修改 + 检查 + 留下可恢复快照
→ 释放锁
```

例如两个 Agent 都要修改 CAN 协议定义、同一 ROS2 消息接口或共享配置，就可要求先拿锁。

优点：降低同时基于旧状态修改共享资源的风险。  
代价：

- 锁太大：所有并行工作退化成串行；
- 锁太小：无法覆盖跨文件、跨模块的不变量；
- Agent 异常停止：锁如何回收？
- 多资源同时加锁：可能死锁；
- 等待锁的 Agent：拿到锁后必须重新读取最新状态。

工程上更合理的答案通常是混合策略：

- 独立模块：并行分支 / worktree；
- 共享接口、配置、数据模型：短时锁或明确的合并顺序；
- 合并后：跑集成测试，检查全局约束。

## 6. “能合并”不代表“系统正确”

这是本讲非常重要的一点。

两项修改即使：

- 改在不同文件；
- Git 可以自动 merge；
- 各自测试都通过；

合起来仍可能违反全局不变量。

在机器人系统中可以类比：

```
控制器 A：提高最大速度
安全模块 B：按旧速度阈值计算制动距离
```

两个提交都可能合理、无文本冲突，但合并后制动安全裕度不足。

所以版本控制最多保证“历史与文本层面可协调”；系统正确性还依赖：

- 明确需求；
- 不变量；
- 接口契约；
- 集成测试；
- 仿真和实际验证。

## 7. 团队变大，困难从编码转向协调

成员数为 \(n\) 时，潜在两两沟通关系约为：

\[ \frac{n(n-1)}{2} \]

所以：

- 3 人：3 条潜在关系；
- 6 人：15 条潜在关系。

这不是说团队一定有这么多会议，而是说明：如果缺少接口、规则和职责边界，协调复杂度会很快上升。

常见失败模式：

- 前端和后端对字段含义、错误处理理解不一致；
- 有人说“完成”指代码写完，有人指测试通过，有人指已经可部署；
- 上游接口迟迟不确定，下游不断返工；
- 每个模块看似都有负责人，但跨模块问题无人接手；
- 一人希望尽快发布，另一人顺手重构，优先级冲突。

因此版本管理工具很重要，但它不替代产品与工程管理。

## 8. 从零做产品：你是“包工头”

Agent 可以写代码，但你仍必须决定：

- 先做什么；
- 哪些需求是第一版必须验证的；
- 模块如何连接；
- 接口是什么；
- 什么结果才算交付成功；
- 哪些设计可以以后更换。

尤其空项目比成熟开源项目难得多，因为它没有现成约束。

例如“会成长的个人助手”这个需求，看似明确，其实仍有很多未决问题：

- “成长”是记住事实、偏好，还是学会新任务？
- 记忆是否永久有效？
- 临时偏好如何过期？
- 用户纠正后如何覆盖旧记忆？
- 助手何时应主动行动？

如果一开始把“所有记忆永久有效”写死，后来才发现偏好有时间和场景限制，就会产生技术债。

> 技术债不一定来自草率；也可能来自你后来才真正理解问题。

所以设计的关键不是“第一次就完美”，而是让系统能承受已知和未知的变化。[jyywiki.cn](https://jyywiki.cn/GSE/2026/lect4.md?utm_source=chatgpt.com)

## 9. MVP：最小可行产品不是“简陋产品”

MVP（Minimum Viable Product）的目的不是做一个看起来最少的东西，而是：

> 用最小成本验证最关键的假设。

开始前应写清：

1. 这个版本到底要验证什么？
2. 什么结果出现时，说明我们原先想错了？

比如对你的 FSAE AMI，不要第一版就做完整仪表盘、所有车辆状态、历史日志、设置菜单和故障诊断。一个更好的 MVP 可以是：

```
接收一条真实/回放 CAN RPM 报文
→ 正确解析
→ 屏幕显示 RPM
→ WS2815B 灯带按 RPM 变色
→ CAN 丢失时进入安全降级状态
```

它能实际验证：

- CAN 报文定义是否正确；
- P4 的任务调度是否够稳定；
- UI 和灯带是否同步；
- 断链后的安全行为是否正确；
- 车手是否真的读得懂、用得上。

真实使用会让“更主动”“更智能”“更好用”这类模糊词变成具体可检验的问题。
